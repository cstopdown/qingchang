# VocalVerse CPU 评分服务部署与验收

2026-10-30 在 citygis-cloud 完成真实 CPU 推理与 HTTP 验收。服务为 `qingchang-vocalverse.service`，仅监听 `127.0.0.1:28787`；独立目录 `/opt/qingchang-vocalverse`，独立虚拟环境，不使用既有 GPU 或 MiniCPM 环境。

## 已实现能力与真实性边界

使用官方 `MuQRegressionAudioLora` 与 `step_3_ktv_rerecord_highscore`，返回原生 **0–100 模型实验分数**。不转换成四维，不生成文字点评，不重新校准原始分数。`summary` 仅说明评分和实际评价片段。

**模型不是人声分类器。** 本次3秒合成三和弦器乐得到79.6188分，高于真人清唱的66.7954分。这说明“能输出数值”不能证明是有效歌唱判断，也不能据此宣称客观唱功、跨音源排序或器乐拒绝能力。静音与不足1秒输入在模型调用前返回 `scorable=false`、`score=null`。1秒是产品输入要求；不足10秒附加不稳定提示，均不声称是经模型验证的阈值。

## 安装与下载

SSH 统一使用 `ssh -J aliyun citygis-cloud`。以下命令在服务端运行，应用源码放在 `/opt/qingchang-vocalverse/source`。

```bash
uv venv /opt/qingchang-vocalverse/venv --python /usr/bin/python3.12
uv pip install --python /opt/qingchang-vocalverse/venv/bin/python \
  --no-deps --index-url https://download.pytorch.org/whl/cpu \
  torch==2.9.1+cpu torchaudio==2.9.1+cpu torchvision==0.24.1+cpu
uv pip install --python /opt/qingchang-vocalverse/venv/bin/python \
  --index-url https://pypi.tuna.tsinghua.edu.cn/simple \
  -r /opt/qingchang-vocalverse/source/vocal_service/requirements.txt
```

CPU 三件套必须独立固定安装。不要对全部依赖使用 PyTorch 索引和 `unsafe-best-match`：本次该方式使普通依赖卡在 Fastly 连接；固定 CPU wheel 后，仅用清华索引安装其余依赖，69秒完成。实际安装清单保存在服务端 `requirements-verified.txt`。真实模块调用链已导入成功，`torch.cuda.is_available()` 为 false。

```bash
cd /opt/qingchang-vocalverse/source
python3 -m vocal_service.download --home /opt/qingchang-vocalverse \
  --endpoint https://hf-mirror.com --phase weights
python3 -m vocal_service.download --home /opt/qingchang-vocalverse --phase source
```

下载器仅使用固定清单，8MiB 分块、最多两个文件并行、有限重试；完整文件 SHA256 验证后才改为最终文件名。下载进度每块输出真实字节，可恢复已有分块；校验失败直接报错。本次 `hf-mirror.com` 权重下载约1.3–1.5MB/s。服务端访问 `raw.githubusercontent.com` 曾 TLS 失败，改由本机按同一清单逐个核验原文后传入 `upstream-original/`，再执行 `--phase source`，没有改变来源版本。

## 运行与接口

将已有网关配对的 `QINGCHANG_AI_TOKEN` 写入独立 `worker.env`，权限600，不写入文档、Git 或日志。不能使用空 token。将已授权验收干声放入 `fixtures/readiness.wav`。安装 [systemd 配置](./qingchang-vocalverse.service)：

```bash
cp vocal_service/qingchang-vocalverse.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now qingchang-vocalverse.service
```

配置：CPUQuota200%、Nice10、MemoryMax16GiB、线程4、并发1；`CUDA_VISIBLE_DEVICES` 为空，HF 与 Transformers 为离线模式。当前已 enable。复用既有反向 SSH 到28787端口，本次未修改它。

`GET /health` 返回 v2 模型身份及 loading/ready/error；只有固定权重校验、模型加载和真实 `readiness.wav` 推理均成功，才进入 ready。`POST /v2/score` 接收唯一 `audio`（干声 WAV）、`recordingId`、`title` multipart 字段，最多100MiB音频加64KiB表单预算。全部请求需 Bearer token，拒绝带 Origin 的直接浏览器请求，由网关代理。

音频转为24kHz单声道，按官方方式将整段 integrated LUFS 归一化至 -12，再以 recordingId 的 SHA1 稳定选择最长90秒片段；短于90秒保留全部，响应返回实际起点和时长。仅接受干声，不使用混音降级。上传错误422、未认证401、忙429、未就绪503、真实推理异常502；没有静默兜底分数。

## 90秒完整模型性能验收

为覆盖用户完整歌曲会触达的90秒上限，将同一20.1405秒 clean WAV 重复拼接、截取到恰好90秒，保持16kHz单声道PCM16。此输入**只用于性能验收，不是真人90秒演唱或评分质量证据**。文件SHA256为 `a49e41a45d9b6d9ccc4582053660dc20f3a884a0fa40d2df1d7d39d321f0cd57`。

在原有 CPUQuota200%、MemoryMax16GiB、4线程、单并发约束下，完整 native API 返回 HTTP200，耗时 **19.0297秒**，原始实验分数 `67.79161834716797`。响应为 `sourceDurationSeconds=90, startSeconds=0, durationSeconds=90, modelCalled=true`，未静默裁短。新 API 首条限制文字也已在这次真实响应中核验。

该进程 cgroup MemoryPeak **3,830,341,632字节（约3.57GiB）**、MemoryCurrent **2,242,306,048字节**；`/proc` VmHWM **3,949,960KiB**、VmRSS **2,404,396KiB**。`memory.events` 的 max、oom、oom_kill、oom_group_kill均为0，服务保持 active，没有OOM或自动重启。原始响应位于服务端 `logs/performance-90s.json`，本机副本为 `.tools/vocalverse-performance-90s.json`；OOM计数保存在 `logs/memory-events-before-90s.txt` 与 `memory-events-after-90s.txt`。

此次发布 API 限制文字后重启了自有 worker，真实20.1405秒清唱再次预热得到相同原分66.79544067382812；加载加预热10.0565秒，其中模型推理3.4918秒。该耗时受已缓存代码和系统文件影响，不能替代首次启动的20.0688秒记录。

## 未验证能力

95秒源音频的稳定90秒裁片已在功能测试中验证，90秒完整模型性能也已按上节实测。仍不能把单次性能结果推广到任意歌曲或系统负载；并发只允许1个请求，长片段期间其他评分请求返回429。最长评价90秒，不是全曲逐段评价，超过90秒的源音频响应会提供实际评价区间。

尚未完成用户本人干声的评分质量验证、跨歌手/曲风校准、人类专家一致性验证或系统性的噪声/混响稳健性评测；已有有限退化对照出现反向排序。器乐反例已说明输出值不代表输入属于歌唱；系统没有四维点评或声源分类能力。
